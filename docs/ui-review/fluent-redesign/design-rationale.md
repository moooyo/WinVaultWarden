# Fluent redesign review rationale

Review date: 2026-09-15. Scope: a visual and interaction proposal for WinVaultWarden, a native Windows password and key manager. This document accompanies proposed review diagrams. It is not evidence that the application has been changed or that the proposed behavior has passed runtime verification.

The baseline is the [source inventory](../page-inventory.md), [original native captures](../index.html), and [runtime findings](../runtime-findings.md). Preserve their evidence status. The baseline has nine reachable pages; dialog, editor, state, native, and external surfaces are not additional existing product pages. The proposal intentionally promotes the existing generator dialog to a dedicated workspace destination. This is an information-architecture change for review, not a newly implemented application route. Existing capability, account, organization, and policy restrictions remain binding.

## Design direction

Use a quiet Windows workspace: a Mica-like shell, opaque content surfaces, restrained blue selection and primary actions, Segoe typography, and thin neutral separators. The distinctive element is a consistent **security context strip**: account, service host, current vault or organization, and a reachable Lock action. It makes the destination and ownership of sensitive actions legible without decorating every screen with security claims.

The three-panel vault remains the central working model. Navigation establishes location, the list establishes selection, and the detail pane supports inspection and precise field actions. A narrower window moves between list and detail while retaining search, selection, and a clear Back action. Form and management pages use the same spacing and command hierarchy rather than copying the vault's columns unnecessarily.

The generator's proposed full workspace makes output, options, and history visible without trapping the task in a small dialog. Password, passphrase, and username remain modes of the existing generator capability. An item editor may later launch a compact derivative that returns the chosen value to its field; that derivative is a future implementation pattern, not a claim about a completed flow. The standalone workspace must retain the same generator settings and history policy rather than creating a second generator system.

This direction follows Fluent's emphasis on platform familiarity, focus, and inclusion. Product-specific safeguards below are design judgments applied to a password manager; they are not claims that Microsoft prescribes a particular secret-management policy. [Fluent design principles](https://fluent2.microsoft.design/design-principles)

## Review decisions

| ID | Baseline or review problem | Proposed behavior and appearance | Implementation review acceptance |
| --- | --- | --- | --- |
| D01 | The current shell offers many similarly weighted destinations; account and server context are not a continuous visual anchor. | Group primary navigation around Vault, Send, Generator, and Security reports. Keep administrative destinations and Lock in a stable lower area. Show the active account and service host in the context strip. Give selection one blue indicator and a low-contrast fill. | An auditor can identify account, host, location, and selected item at a glance. Context survives navigation, organization changes, narrow layouts, and dialogs. Lock stays reachable without opening a menu. No new supported feature is implied. |
| D02 | The overview captures show weak separation between shell, list, and content, while page spacing varies. | Use a Mica foundation only for the shell/title bar and an opaque standard content layer. Use section cards where grouping helps, not one card per sentence. Reduce decorative shadows and reserve elevation for temporary overlays. | A native implementation uses theme resources and supported materials, with solid fallbacks. Content remains readable when inactive, transparency is disabled, or high contrast is enabled. The static mockup's tint is identified as an approximation. |
| D03 | Vault rows, filters, and detail actions compete for attention; empty selection uses a large amount of unstructured space. | Put page title, scoped search, result count, and primary Add action in a consistent header. Keep list title and secondary account/domain text aligned. Keep the selected item header and key commands stable above grouped fields. Empty states explain the next useful action. | Search and filter changes preserve predictable selection behavior. Opening and closing details does not lose list position. A narrow layout provides Back to results. Primary actions and menus remain reachable without horizontal scrolling. |
| D04 | Runtime finding 2 records a missing password row and unavailable TOTP after reprompt, despite verified field presence. | Keep a stable password/TOTP row before authorization. Distinguish Protected, Not configured, Loading, and Unavailable. A protected row explains the required verification and offers Unlock sensitive fields. After authorization, transition in place to masked password and available TOTP. | Layout and action positions do not jump on reprompt. Reveal and Copy require the actual authorization policy. No secret appears in feedback, logs, placeholders, or accessible control names. TOTP has textual time remaining as well as a visual indicator. The known rendering failure must be separately fixed and verified. |
| D05 | Field actions need immediate, unambiguous feedback without exposing the value or obscuring the next task. | Use aligned Reveal, Copy, and Open actions with distinct accessible names. Show compact field-specific feedback such as Password copied. If a timed-clear policy is active, display its real duration, not a fixed promise. Keep feedback adjacent or in a nonblocking status area. | Copy feedback follows a successful clipboard write, never the button press alone. Failure is explicit. A new copy replaces the preceding status. Clipboard timeout messaging reflects the actual configured policy. Do not announce that content was cleared until the service confirms it; never clear unrelated clipboard data. |
| D06 | Authentication has many conditional stages; the generator and Send editor have clipped content in native captures. | Use an authentication panel with account/host continuity and one stage-specific primary action. Promote the generator to a dedicated workspace with output, options, and history in a scrollable layout. Give Send forms bounded scrolling content and a visible command footer. Reveal advanced settings on demand. Keep required fields and current output above optional controls. | At narrow widths and increased text scaling, controls wrap or stack without clipping. All form content remains scrollable and all commands reachable. Tab selection preserves input. The generator workspace is an explicit proposed route change; a later editor-launched compact derivative should reuse its settings and output behavior. Conditional authentication and policy stages retain their real prerequisites. The generator clipping and blank editor remain separate runtime issues. |
| D07 | Security reports present several expanders with similar weight; the captured report expansion also has an unresolved runtime exit. | Make findings actionable: state the issue, affected-item count, and the action that opens those items. Separate local analysis from an optional external exposure check. Show when a check was last completed and explicit Not checked, Checking, and Could not complete states. Avoid an invented overall security score. | Counts link to actual result sets. Color is paired with icon and text. A partial check never becomes an all-clear message. Empty results say which checks ran. Proposed expanded results are not represented as successful native captures until the runtime exit is fixed. |
| D08 | Settings form a long scrolling page; account security, preferences, and dangerous actions can blend together. | Add local section navigation or anchors for the existing six sections. Use label, brief consequence, current value, and action in a consistent row. Separate policy-constrained, unavailable, and enabled states. Put Danger zone last with localized warning emphasis. | Section navigation preserves a single coherent settings route. Every disabled feature explains the actual reason. Future controls stay visibly unavailable. The diagram does not invent working language, SSH-agent, startup, or unsupported browser-integration features. |
| D09 | Devices, emergency access, and Send contain state-dependent actions whose consequences differ substantially. | Use explicit status labels and compact metadata rows. Devices emphasize the current device and pending-request identity. Emergency access separates people who can access this vault from accounts that trust this user, with permission and waiting period visible. Sends expose type, expiry, and access limits before secondary details. | Buttons correspond only to valid states. Device approval preserves fingerprint comparison. Emergency recovery clearly distinguishes read-only View from Takeover. Passkey approval retains RP ID, account selection, origin context, and cross-origin warnings. No unsupported invitation-acceptance page is added. |
| D10 | Export, deletion, trust, takeover, and ordinary edits should not have equal visual severity or confirmation cost. | Use inline validation for field errors and a ContentDialog for material confirmation or required verification. Explain the object, consequence, and scope. Keep a safe Cancel action on the right and a specific execution action on the left. Destructive confirmation uses localized warning styling and does not default Enter to the dangerous action. | Reversible deletion and permanent deletion use different wording. Export states format and plaintext consequences before verification. Confirmation reuses the real authentication requirements. On cancel, focus returns to the triggering control. There is one dialog per window and no concealed destructive default. |

Decisions D01-D03 apply Fluent's focus and neutral hierarchy. D02 follows Windows Mica layering. D04-D05 and D09 combine the documented product inventory with security-oriented design judgment. D06-D08 use Fluent hierarchy and native keyboard/accessibility guidance. D10 follows ContentDialog guidance; the choice to avoid a destructive default is a product safety judgment. - Typography: Segoe UI Variable Display for titles; Segoe UI Variable Text / Segoe UI for body and controls; Cascadia Code / Cascadia Mono / Consolas only for generated strings, fingerprints, and identifiers. The prototype uses 28/36 page titles, 23/31 secondary headings, 16/24 section headings, and 14/20 body text, with 11-12 pixel metadata and 13 pixel dense values. These are the prototype's actual choices; the documented Windows ramp instead specifies a 20/28 subtitle and 12/16 caption. Keep primary values readable, and review smaller metadata with text scaling rather than treating screenshot fit as an accessibility pass. [Fluent typography](https://fluent2.microsoft.design/typography)
- Spacing: the 1280 by 900 pixel review viewport uses a 219 pixel navigation column, a 330 pixel vault list, 30 by 36 pixel main-page padding, and 28 pixel detail gutters. The layout combines 4, 8, 12, 16, 20, 24, 28, and 32 pixel spacing intervals. These are project proposal values, not a claim about mandatory platform dimensions; a native implementation should express its scaled geometry in DIP.
- Shape: the prototype uses 6 pixel action-button corners, 5 pixel field corners, 9 pixel section corners, and 12 pixel window/dialog corners. Let Windows own the actual native window frame. Avoid large capsules for ordinary actions and avoid arbitrary heavy drop shadows.
- Density: comfortable default row spacing; keep key actions visible and let content scroll. The proposed detail pane should not shrink until field values and actions overlap. Retain the product's existing responsive route behavior while reviewing exact content-driven breakpoints.
- Motion: brief state changes only for selection, pane transition, and feedback. Keep output and action positions stable, and honor reduced-motion preferences. Do not animate secrets character by character or use motion as the sole state signal.

Fluent recommends neutral hierarchy, sparing brand/semantic colors, and multiple cues for state. It also distinguishes Windows interaction colors from web interaction colors; the mockups are a native Windows proposal, not a wholesale use of web component states. ## Keyboard, focus, and accessible review contract

Use native controls whenever possible. Tab and Shift+Tab move in visual task order; arrow keys navigate the vault list and familiar grouped controls. Show a visible focus border distinct from selection. On narrow-layout Back, restore the selected row and list position. On dialog dismissal, restore the trigger; on validation failure, focus the first invalid field and provide an associated message. Do not shift focus to passive copy feedback.

Proposed accelerators may expose Search (`Ctrl+F`), New item (`Ctrl+N`), and Lock (`Ctrl+L`), subject to conflict review and implementation. They are design suggestions, not a claim that the current app implements them. Do not assign an easy accidental global accelerator to reveal secrets, approve a device, or permanently delete data. A focused field's Copy action may have an explicit accessible shortcut; ordinary text-copy behavior must remain predictable.

All icon actions need names that identify the action and field, for example Copy username or Reveal password. The name must not contain the secret. Status changes need screen-reader announcements at appropriate urgency without moving focus. TOTP should not announce every second. Warnings need text and an icon, not color alone. Verify the implementation with Narrator, keyboard-only input, system text scaling, dark theme, and high contrast. These are future acceptance checks, not completed checks for the visual proposal. [Windows keyboard guidance](https://learn.microsoft.com/en-us/windows/apps/design/input/keyboard-interactions), [Windows accessibility overview](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-overview)

## Runtime issues remain independent

| Existing finding | Visual response in the proposal | Required engineering follow-up |
| --- | --- | --- |
| HTTP 429 presented as credential failure | Distinct throttling message and retry timing when known | Correct error classification and retry behavior |
| Password/TOTP absent after reprompt | Stable sensitive-field rows and explicit authorization/loading/error states | Diagnose and fix the projection, binding, or rendering failure |
| Blank login editor pane | Complete editor structure with persistent Save/Cancel footer | Diagnose and verify editor initialization |
| Generator controls clipped | Dedicated generator workspace with responsive options and a scrolling content area | Implement the intentional route change and verify layout at actual window sizes and text scaling; reuse generation behavior in any later compact editor derivative |
| Reused-password expansion followed by exit | Proposed actionable result body | Diagnose exit and verify expansion separately |
| Secure-note text duplicated | Show one canonical Content section | Remove duplicate presentation and verify other item types |
| Trash navigation followed by exit | Proposed Trash state with Restore and permanent-delete actions | Diagnose exit and verify navigation separately |

The redesigned images describe intended UI and interaction. They do not change these observations into passes, prove clipboard or encryption guarantees, certify accessibility, or establish end-to-end API compatibility. Native Windows Hello, WebAuthn, file pickers, browser SSO, and third-party pages should retain clearly labeled host-owned boundaries rather than fabricated internal screens.
