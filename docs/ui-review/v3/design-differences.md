# v3 design differences and decisions

## Review basis

This review compares the v3 handoff and [design specification](design-spec.md) with the delivered native WinUI source and actual application captures. The observed implementation and packaging defects were corrected and recaptured. [Native results](native-results.json) and [delivery evidence](README.md) identify the final executable, successful scope and unexercised external workflows. This is a practical main-page review, not a claim that every possible provider, error state or screen size was exercised.

The reference uses native system capabilities, real service results, and existing security gates in preference to simulated prototype behavior. A missing feature is not an acceptable reason to claim a successful action. Fixable presentation/integration defects are separate from backend or platform capability limits.

## Actual capability differences and decision options

| ID | Reference behavior | Current supported behavior and reason | Recommended decision | Alternative |
| --- | --- | --- | --- | --- |
| C01 | Full OpenSSH agent, key loading, signing prompts, remembered executable/host grants, forwarding detection and request history. | SSH keys can be stored/viewed/copied. No actual signing-agent service exists. Settings honestly reports this; the status bar must not claim running/loaded keys. Host identity and forwarding additionally require OpenSSH session binding and trusted host-key mapping. | Keep SSH unavailable in this UI delivery and scope the agent as a separate security-reviewed feature. | Implement and verify the complete named-pipe protocol, host identity, executable authorization, key lifecycle and queue before enabling the controls. |
| C02 | Report entries for supported websites lacking saved two-step verification, plus an Add verification code copy cell. | There is no authoritative site-capability dataset. Absence of saved TOTP alone does not prove that a site supports or lacks two-step verification. The handoff explicitly permits omission. | Omit this category and claim until a maintained source exists. | Add a maintained/attributed dataset and a domain-matching/update policy, then enable the UI. |
| C03 | Eight import formats, choosing a destination folder, account-bound encrypted export, password-protected export. | The service contracts currently support Bitwarden JSON and CSV only. Import preserves folders in the source. Export is plaintext; the UI now describes this accurately. | Expose only these actual formats with clear protection warnings and retain the real preview/master-password/save-picker flow. | Implement and verify importers, folder remapping, both encrypted export contracts and round-trip compatibility as a separate data feature. |
| C04 | Argon2id parameter editor and choice of PBKDF2/Argon2id. | The ordinary account service exposes a PBKDF2 transition, not a complete algorithm/parameter editor. The corrected UI shows actual current parameters and blocks unsupported Argon2id editing. | Keep unsupported algorithms/parameters unavailable and identify current KDF correctly. | Add the complete Argon2id write/reencryption contract and compatibility tests before exposing the choice. |
| C05 | Optional account-key rotation during master-password change; current device remains signed in after password/KDF changes. | Account-key rotation is unavailable. The existing successful credential-change transaction intentionally uses `CredentialChanged` to sign this device out as well. | Keep key rotation disabled and retain current logout behavior with explicit success copy. | Implement account-key rotation and a reviewed session/token continuation transaction. This is a security/workflow decision, not a cosmetic toggle. |
| C06 | Five display languages, startup setting, hardware-acceleration toggle. | Localization resources and platform-backed startup/GPU preferences are not implemented. Controls now state that they are unavailable rather than storing ineffective settings. | Keep them disabled or omit them from everyday controls while preserving an explanation. | Implement and verify each platform feature before enabling it. |
| C07 | Browser integration enabled regardless of installation mode. | The existing architecture supports paired browser integration in the unpackaged build; MSIX is restricted. | Keep the packaged capability gate and explain the supported install mode. | Add and verify package-aware native-host registration and lifecycle support. |
| C08 | Send deletion has an eight-second Undo action. | The real server deletion is irreversible. Reinserting local demonstration data would not restore the same encrypted Send or its link. | Retain an explicit permanent-delete confirmation and no misleading Undo. | Design a delayed server commit with cancelable deletion or a documented replacement Send, carefully handling expiry, sessions, restarts and changed links. |
| C09 | Send sort and subtitle use creation time. | Vaultwarden stores a creation date internally but its current Send JSON projection exposes revision/deletion data, not that date. The app accurately labels its order as recently modified. | Label and sort by the actual available timestamp; do not present revision time as creation time. | Record local first-seen/create metadata, clearly distinguishing it from a server-authoritative creation date. |
| C10 | Device list shows client version, location, last active and per-device Remove that revokes login. | The authoritative current device response does not provide all of these facts, and no per-device session-revocation endpoint was identified. Real request IP/creation/fingerprint data is available. | Show only known facts and supported operations; avoid fabricated location/activity/version or session-revocation success. | Implement additional supported server contracts if available, or separately implement a confirmed all-session security-stamp revocation flow. That all-session action is not currently connected. |
| C11 | External device approval window can appear while the vault is locked, minimized or tray-hidden and offers Unlock and approve. | The current request presentation is bound to an unlocked session lease, and lock closes it. Existing minimize/close-to-tray behavior locks first, so those background scenarios are also unavailable. | Retain the safer unlocked-only behavior for this delivery and label the difference. | Add a separate account-bound, metadata-only locked-request lifecycle, then reacquire an unlocked lease and revalidate request identity immediately before approval. |
| C12 | About checks for updates and confidently reports latest status. | No automatic-update mechanism is implemented. The UI opens the release page instead. | Retain an honest Open releases action. | Add a signed/verifiable distribution-aware update check and failure/availability states. |
| C13 | PIN setup accepts at least four characters, offers a default-on master-password-first-after-restart policy, and logs out after five failures. | `PinService` persists the PIN-wrapped user key in the protected token store, and `AuthService` loads it for local unlock after restart. Current minimum length is six. The master-password-first-after-restart option is unavailable; the settings UI correctly shows it disabled/off. Five failures clear the stored PIN and return to other available unlock methods rather than fully logging out; an enrolled Hello method can remain available. | Preserve the six-character minimum and current five-failure lockout. Clearly disclose restart-persistent PIN behavior; leave PIN off if master-password-first-after-restart is required. | Add a reviewed memory-only PIN wrapper/restart gate for the reference policy and explicitly decide whether five failures should fully log out. Do not describe the current wrapper as memory-only. |
| C14 | Hello/PIN local unlock is offered without demonstrating account-key-version limits. | Both actual local-unlock services currently reject the newer V2 account-key path. Hello onboarding explains eligibility and offers a real skip option; settings disables unsupported PIN/Hello. | Retain these eligibility gates and use the master password for V2 accounts. | Implement and verify V2 key protection and cancellation-safe OS enrollment before enabling those paths. |

## Intentional native and security-policy differences

- Native Windows Hello appearance, window shadow, system caption buttons, system accent, Mica, menu metrics, and high-contrast presentation follow the OS. The handoff explicitly requests native system UI; these are expected platform variations rather than imitation defects.
- Master-password fallback remains necessary where Windows Hello is not enrolled/available. A simulated verification dialog must never replace actual user verification.
- Existing Bitwarden reprompt protections and the account-deletion multi-step flow remain intact even though the prototype simplifies them. The handoff explicitly says to preserve them.
- Device approval adds an explicit fingerprint-reviewed checkbox and places Deny before Approve. This is a deliberate confirmation policy, not a platform restriction. Retaining it is recommended; matching the prototype's simpler layout would require a conscious policy change.
- HTTP URL findings, organization/collection features, extended item types, custom-field management, password history, attachment writes, browser passkey UI, tray behavior, licenses, and other handoff-excluded surfaces remain supported rather than being removed to match a smaller prototype inventory.
- Existing minimize/close-to-tray behavior locks the vault and clears owned clipboard data. Copy-then-minimize is therefore currently unavailable and its settings control is disabled. Implementing that interaction requires an explicit decision about the lock/clipboard policy; it is not a Windows capability limit.
- Diagnostic/version/server information must come from real runtime/account state. Prototype numbers, dates, identities, exposure counts, QR placeholders and prefilled demo URLs are not acceptable substitutes.

## Acceptance status

The delivered application contains the native four-tab shell, contextual pane, content layer, shared visual tokens, copy-strip control, inline Vault/Send editors, settings sections/subpages, and independent device-request window. Release publishing, 4,700 automated tests, and the explicitly recorded native execution scope passed. Nine selected native images and six separately labeled earlier supplemental images support the review.

Seventy [prototype reference captures](reference/README.md) are available in light/dark at 1280 x 760, 1024 x 720 and 760 x 640, including authentication and wide/narrow inline editor flows. Their manifest validates crop sizes and labels every record `referenceOnly`. These help comparison but are not native implementation evidence.

The [review ledger](review-checklist.md) records native observations, source/automated coverage and unexercised paths. The C-series table carries the remaining product/capability decisions forward without representing them as impossible future work.
